Motion for SacraDigit

These are suggested animations, transitions and loading states for the Admin, Parishioner, Media and ITech portals. Every card has a live demo built from the system's own navy, gold and burgundy palette, plus the CSS for it and the file where it belongs. Motion here should feel reverent and calm: soft fades, gentle rises and gold accents. Avoid bouncy, game-like effects.

Motion tokens

Right now each stylesheet picks its own timing (0.15s ease, 0.25s ease, 0.12s…). Define these once in a shared file such as accessibility.css or a new motion.css so every portal moves the same way. Hover a row to preview it.

Loading screens

Three tiers. A branded splash shows once per session; skeletons cover data fetches from Amplify; inline spinners cover actions. Never show a full-screen loader for something that takes under 300ms.

Branded splash (first load) P1

A refined version of loading screen test/. The progress bar should follow real stages: auth check, then parish info, then the dashboard. Rotate the status text through those stages, and fade out with a 300ms opacity transition once auth.js resolves.

Show only when sessionStorage.sdSplashSeen is not set. Repeat visits skip straight to skeletons. Use it in index.html, login.html → dashboard, and the PWA launch (pwa.js).

Skeleton screens P1

Gray placeholder shapes in the same layout as the real content, then a staggered fade-in when the data arrives. Use them for dashboard KPI tiles, request tables, Digital Archives and the Media Library grid.

Add a .sk utility to the shell CSS files. Render skeleton rows in table-cards.js before the fetch resolves. Keep the skeleton up for at least 300ms so it doesn't flash.
CSS
.sk { background: linear-gradient(90deg,#e5e7eb,#fff,#e5e7eb);
  background-size: 200% 100%;
  animation: shimmer 1.4s linear infinite; border-radius: 6px; }
@keyframes shimmer { from { background-position: 200% 0 }
                     to   { background-position: -200% 0 } }

Top progress bar P2

A thin gold bar along the top edge when you click a sidebar link. Every portal page is a separate HTML file, so this tells users the click registered while the next page loads.

Start it on sidebar link click in admin-ui.js, user-shell.js, media-shell.js and the ITech shell. It's about 15 lines of JS and needs no library.

Button busy → success P1

When a request, donation or intention is submitted, the button shows a spinner and is disabled, which also prevents double submits. It then turns green with a drawn check and the label "Submitted".

Use for all submit buttons in certificate-step-forms.js, mass-intention-form.js, marriage-request-form.js, donation-payment-info.js and the facility booking forms.

OCR / document scan progress P2

A gold scan line sweeps over the uploaded record while OCR runs, and lines light up as text is extracted. Users see the work happening instead of a frozen screen.

ocr/, Sacradigit/scanner, document-scanner.css and the Digital Archives upload.

Page transitions

SacraDigit is a multi-page app, with one HTML file per screen. This makes the browser's cross-document View Transitions API a free win: two lines of CSS and pages crossfade instead of flashing white. Browsers that don't support it fall back to normal navigation.

Cross-page crossfade P1

The sidebar and top bar stay put while only the content area fades and slides. This removes the white flash between pages.

Add to every shell CSS (admin-shell.css, user-shell.css, media-shell.css, itech-shell.css).
CSS
@view-transition { navigation: auto; }
.sidebar  { view-transition-name: sidebar; }
.top-bar  { view-transition-name: topbar; }
main      { view-transition-name: page; }
::view-transition-old(page) { animation: 160ms ease-in both vt-out; }
::view-transition-new(page) { animation: 240ms cubic-bezier(.22,1,.36,1) both vt-in; }
@keyframes vt-out { to   { opacity: 0; transform: translateX(-12px); } }
@keyframes vt-in  { from { opacity: 0; transform: translateX(12px); } }

Staggered content enter P1

The page title, then KPI tiles, then panels rise 8px and fade in, 60ms apart. Cap it at about 6 items and show the rest at once.

Dashboards: dashboard.js, user-dashboard.js, media-dashboard.js, itech-dashboard.js. Set style="--i:n" and use animation-delay: calc(var(--i) * 60ms).

Accessibility rules

Many parishioners are older and some use the site on low-end phones. These rules are non-negotiable. Try the "Simulate reduced motion" button in the sidebar.

Respect prefers-reduced-motionAdd one global rule that collapses durations to 0.01ms, plus a "Reduce motion" toggle in ui-prefs.js next to the theme and language options. Only part of the current CSS handles this.
Only animate transform & opacityNever animate width, top or height on large elements. These cause jank on cheap Android phones. The progress bar is the one small exception.
Nothing over 400ms on repeat actionsReserve the 700ms scene duration for once-in-a-while celebrations. Staff click through queues all day, so their motion has to be fast.
Loading must be announcedSkeletons and spinners get aria-busy="true" on the container, plus a visually hidden "Loading requests…" in an aria-live="polite" region.
Never block inputUsers can click or scroll through any animation. The splash is skipped when it's not the first visit or once the data is ready.
No infinite motion in viewInfinite loops are allowed only for real ongoing state: Pending dot, LIVE, loading. Pause them when the tab is hidden.
