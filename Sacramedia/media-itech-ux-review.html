ITech portal Critical

This portal decides who can see parishioners' personal records, so mistakes here are security mistakes.

I1 "Roles & Permissions" saves permissions that nothing checksHighITech

The page lets IT create roles and tick permissions, but those Role records are only read by the Roles page itself. What someone can actually do comes from the four fixed account roles (Head Admin, Secretary, IT Team, Media Team). Deleting a role even warns "Assigned users lose these permissions", which isn't true. IT can believe someone is restricted when they aren't.

After — say what's real
What each account role can do
Secretary
Records, requests, bookings, drafts. Can't approve, publish or delete.
Head Admin
Everything the Secretary can, plus approve, publish, delete.
Either make the table read-only and accurate (recommended), or wire custom permissions into auth.js — a much bigger job.

No database match for "permissions that aren't enforced". General guidance; nearest rule: Compact Control Semantics ("controls must expose state that matches the visible label", Critical).
I2 Changing a role is just picking from a dropdown in the tableHighITech

Each account row has a role picker; the change starts as soon as a new value is picked. Arrow keys or a scroll wheel over a focused picker can select "Head Admin" by accident, and the browser box that follows is easy to OK without reading. Giving someone Head Admin access deserves a deliberate step.
